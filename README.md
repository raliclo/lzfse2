# lzfse2

English | [繁體中文](README.zh-TW.md)

`lzfse2` is an LZFSE command line compression/decompression tool enabled in Swift. It contains bit-compatible, multi-core encoders and decoders, and also provides optional private `bvx3` format in exchange for higher compression rates.

## Function

- `other3` is the default engine, output standard LZFSE stream, which can be decoded by Apple Compression and this tool.
- `other3 -optimal3` is the DP optimal analysis mode of the standard LZFSE format; the compression rate is better than that of the general `other3`, and the output is still compatible with Apple.
- `apple` Use Apple `COMPRESSION_LZFSE` when available.
- `bvx3` uses private expansion blocks with larger windows and alphabets. The compression rate may be better, but only this tool can decode it.
- `bvx3 -lazy2` and `bvx3 -optimal` are private format high compression rate parser modes, which are suitable for offline compression with compression priority.
- The decoder accepts all supported block types, including the LZFSE stream generated by Apple.
- Support files, stdin/stdout streaming, and built-in round-trip and compatibility tests.

## Build

Directly use Swift to compile:

```sh
swiftc -O lzfse-cli.swift -o lzfse
```

`-O` flag enables optimized, including `@inline(__always)` instructions to improve hotspot path performance (FSE coding, byte serialization, decoding). See [OPTIMIZATION.md](OPTIMIZATION.md) for details.

Or execute the auxiliary script:

```sh
./compile.zsh
```

`compile.zsh` will also copy the binary file to `/opt/homebrew/bin`, so this step may require local write authority.

## Usage

```sh
./lzfse -h
```

```text
Usage: lzfse -encode|-decode [-algo apple|other3|bvx3] [-lazy2|-optimal|-optimal3] [-si|-i input] [-so|-o output] [-test] [-h]
```

Use the default `other3` engine to compress the file:

```sh
./lzfse -encode -i input_file -o output_file.lzfse
```

Specify engine compression:

```sh
./lzfse -encode -algo apple -i input_file -o output_file.lzfse.apple
./lzfse -encode -algo bvx3 -i input_file -o output_file.lzfse.bvx3
```

Use the standard LZFSE format Optimal3 parser (Apple compatible, but slower compression):

```sh
./lzfse -encode -algo other3 -optimal3 -i input_file -o output_file.lzfse.other3.optimal3
```

Use `bvx3` high compression rate parser mode to compress tar stream:

```sh
tar -cf - input_dir | ./lzfse -encode -si -o input_dir.lazy2.lzfse -algo bvx3 -lazy2
tar -cf - input_dir | ./lzfse -encode -si -o input_dir.optimal.lzfse -algo bvx3 -optimal
```

Unzid the file:

```sh
./lzfse -decode -i input_file.lzfse -o output_file
```

Decompress `bvx3` product:

```sh
./lzfse -decode -i file.lzfse -o out.tar -algo bvx3
```

The built-in decoding path of the same tool can also solve the standard LZFSE stream generated by `-algo apple` or Apple Compression:

```sh
./lzfse -decode -i file.lzfse.apple -o out.tar -algo bvx3
```

Streaming through stdin/stdout:

```sh
cat input_file | ./lzfse -encode -si -so > output_file.lzfse
./lzfse -decode -i input_file.lzfse -so > output_file
```

`-optimal3` is just **other3 encoder's parser / match selection mode**. It uses DP optimal analysis to improve the compression ratio, but the output is still the standard LZFSE / bvx2 bitstream, so the decompression end is the same as the general `other3`, and there is no need to add `-optimal3`:

```bash
./lzfse -encode -i a.tar -o a.lzfse.other3.optimal3 -algo other3 -optimal3
./lzfse -decode -i a.lzfse.other3.optimal3 -so
```

`-lazy2` and `-optimal` are just **bvx3 encoder's parser / match selection mode**, and do not change the `bvx3` bitstream format. The pressed file is still in `bvx3` private format, so you only need to specify `-algo bvx3` when decompressing:

```bash
./lzfse -decode -i file.lzfse -o out.tar -algo bvx3
```

That is:

```bash
./lzfse -encode -si -o a.lazy2.lzfse -algo bvx3 -lazy2
./lzfse -decode -i a.lazy2.lzfse -so -algo bvx3
```

```bash
./lzfse -encode -si -o a.optimal.lzfse -algo bvx3 -optimal
./lzfse -decode -i a.optimal.lzfse -so -algo bvx3
```

The decompression end does not need and should not add `-lazy2` or `-optimal`. These two flags have no format meaning for decode.

### Notes on unpacking Windows PowerShell tar

Do not use `.\lzfse.exe -decode -so | tar ...` directly in Windows PowerShell. PowerShell may use binary stdout as a text pipeline and destroy the tar stream. Please use `cmd /d /c` instead to let the binary pipe be handled by `cmd.exe`:

```powershell
cmd /d /c ".\lzfse.exe -decode -i ""C:/path/input.lzfse"" -n 8 -so | tar -xf - -C ""C:/path/output-folder"""
```

If the seal is created with the relative path of the parent layer, the content path may be `../name/...`; Windows bsdtar will return `Path contains '..'` due to security check. In this case, please remove the front `..` path component when unpacking:

```powershell
cmd /d /c ".\lzfse.exe -decode -i ""C:/path/input.lzfse"" -n 8 -so | tar -xf - --strip-components 1 -C ""C:/path/output-folder"""
```

### Decode tar archive to directory / Decode tar archive to directory

```sh
# 正常解壓 / Normal decode

lzfse -decode -i file.lzfse -debug -so 2>debug/decode_debug.txt | tar -xf - -C /dest
```


## Engine

| Engine | Output Compatibility | Description |
| --- | --- | --- |
| `other3` | Standard LZFSE | Default. Multi-core, lazy matching, the output can be decoded by Apple. |
| `other3 -optimal3` | Standard LZFSE | DP optimal analysis in the standard format; the compression ratio is better than Other3, but the encode is slower and the RSS is higher. |
| `apple` | Standard LZFSE | Use Apple Compression framework. |
| `bvx3` | Private format of this tool | Larger windows and alphabets can improve the compression rate; Apple cannot decode it. |

The positioning of `other3 -optimal3` is "the optimal parse that can be done in the standard compatible format". It is not equivalent to `bvx3 -optimal`: the latter uses private bvx3 `encodeBlockV3`, greater match length and distance expression ability, so the compression ratio can still be significantly better than Optimal3, but it is not compatible with Apple.

When encoding `bvx3`, `-lazy2` and `-optimal` will choose a slower parser mode that may improve the compression rate. THEY WILL NOT CREATE DIFFERENT DECODING FORMATS; GENERALLY, `bvx3`, `bvx3 -lazy2`, `bvx3 -optimal` PRODUCTS ARE DECODED BY `-algo bvx3`.

When decoding, `-algo other3` and `-algo bvx3` use the same built-in block decoder. This decoder accepts all supported LZFSE block types, including standard streams generated by `-algo apple` or Apple Compression. `-algo apple` will switch to Apple framework decoder.


## zsh auxiliary function

This repository contains a `zshrc` example. The directory can be packaged as a `tar` stream first, and then handed over to this tool for compression.

```zsh
# 解壓常見封存格式。
extract () {
    if [ -f "$1" ] ; then
        case "$1" in
            *.lzfse.other3.optimal3) echo "lzfse -decode -i $1 -so -algo other3 | tar -xf - " ; lzfse -decode -i "$1" -so -algo other3 | tar -xf - ;;
            *.lzfse.bvx3.optimal)   echo "lzfse -decode -i $1 -so -algo bvx3   | tar -xf - " ; lzfse -decode -i "$1" -so -algo bvx3   | tar -xf - ;;
            *.lzfse.bvx3.lazy2)     echo "lzfse -decode -i $1 -so -algo bvx3   | tar -xf - " ; lzfse -decode -i "$1" -so -algo bvx3   | tar -xf - ;;
            *.lzfse.bvx3)      echo "lzfse -decode -i $1 -so -algo bvx3   | tar -xf - " ; lzfse -decode -i $1 -so -algo bvx3   | tar -xf -  ;;
            *.lzfse.other3)    echo "lzfse -decode -i $1 -so -algo other3 | tar -xf - " ; lzfse -decode -i $1 -so -algo other3 | tar -xf -  ;;
            *.lzfse.apple)     echo "lzfse -decode -i $1 -so -algo apple  | tar -xf - " ; lzfse -decode -i $1 -so -algo apple  | tar -xf -  ;;
            *.tar.lz4)         lz4 -T0 -d -q -c "$1" | tar -xf - ;;
            *.zst)             zstd -d -c "$1" | tar -xf - ;;
            *.tar.xz)          tar xf "$1" ;;
            *.tar.bz2)         tar xjf "$1" ;;
            *.tar.gz|*.tgz)    tar xzf "$1" ;;
            *.bz2)             bunzip2 "$1" ;;
            *.rar)             unrar e "$1" ;;
            *.gz)              gunzip "$1" ;;
            *.tar)             tar xf "$1" ;;
            *.tbz2)            tar xjf "$1" ;;
            *.zip)             unzip "$1" ;;
            *.Z)               uncompress "$1" ;;
            *.xz)              xz -d "$1" ;;
            *.7z)              7z x "$1" ;;
            *.lz4)             unlz4 "$1" ;;
            *.lzma)            tar --lzma -xvf "$1" ;;
            *.lz4a)            unlz4a "$1" ;;
            *)                 echo "'$1' cannot be extracted via extract()" ;;
        esac
    else
        echo "'$1' is not a valid file"
    fi
}

# 將檔案或目錄打成 tar 串流後，以 LZFSE 壓縮。
lzfseX() {
    if [[ -z "$1" ]]; then
        echo "Usage: lzfseX <file-or-directory> [apple|other3|optimal3|bvx3|lazy2|optimal]"
        return 1
    fi

    local algo="${2:-other3}"
    local extension="lzfse.other3"
    local flags=("-algo" "$algo")
    [[ "$algo" == "apple" ]] && extension="lzfse.apple"
    [[ "$algo" == "bvx3" ]] && extension="lzfse.bvx3"
    [[ "$algo" == "other3" ]] && extension="lzfse.other3"
    [[ "$algo" == "optimal3" ]] && extension="lzfse.other3.optimal3" && flags=("-algo" "other3" "-optimal3")
    [[ "$algo" == "lazy2" ]] && extension="lzfse.bvx3.lazy2" && flags=("-algo" "bvx3" "-lazy2")
    [[ "$algo" == "optimal" ]] && extension="lzfse.bvx3.optimal" && flags=("-algo" "bvx3" "-optimal")

    echo tar -cf - -C "$(dirname "$1")" "$(basename "$1")" "|" lzfse -encode -si -o "$1.$extension" "${flags[@]}"
    tar -cf - -C "$(dirname "$1")" "$(basename "$1")" | lzfse -encode -si -o "$1.$extension" "${flags[@]}"

    echo "--- 壓縮資訊 ---"
    du -sh "$1"
    du -sh "$1.$extension"
}
```

### RSS and CPU energy consumption trade-off

According to the continuous access estimate of [ `LPDDR_power_estimation/LPDDR_power_info.md`](LPDDR_power_estimation/LPDDR_power_info.md), LPDDR4X / LPDDR5 is about `150 / 120 mW/GB`. RSS increased from about 60 MB to 300 MB, with an increase of about 240 MB (0.234 GB), corresponding to the additional power of DRAM of about `35 / 28 mW`.

If the additional cost of about 20–40% of memory controller / PHY is included, the memory subsystem increment is about `34–49 mW`. Even if this is regarded as the conservative upper limit of the continuous activity of the whole segment, about `1.4–2.0 J` is increased by 40 seconds; if it is only about 4 seconds, it is about `0.14–0.20 J`.

In the previous controlled round, when Optimal decode was upgraded from n4 to n40, RSS was about `68.5 / 71.1 MB` Rise to `308.9 / 348.9 MB`, CPU energy is by `17.13 / 11.33 J` Down to `8.39 / 5.86 J` (About `-51% / -48%`). The CPU savings level is much higher than the estimated memory increment of about one hundredth of joules in less than 1 second. Therefore, in the current desktop test and about 300 MB RSS range, giving priority to reducing CPU running time/total energy consumption is a better overall choice, and about 300 MB RSS can be considered conditionally acceptable.

This is a model estimate based on the active-memory unit power consumption, not the actual measurement of this round of DRAM; RSS is not equal to the continuous reading and writing of all pages. The conclusion is only used for energy trade-off, which does not mean that memory capacity, system memory pressure or multi-workload parallel problems can be ignored. The latest best-points Optimal encode n40 RSS is `589.3 MB` (claw-code) and `575.0 MB` (llama.cpp) - taken from the "Highest Encode RSS" column of `best_points/best_points.md` - still obviously exceeds the 300 MB benchmark, and the DP buffer, chunk in-flight and temporary array life cycle should continue to be investigated.

### Applicable scenario: server-side update package compression

Optimal compression is suitable for the distribution model of "server-side compression once, client-side download and decompression many times", such as large server-side code update, App or game update package, CDN static assets. High-cost encode can be completed offline on the release terminal, and it is shared by a large number of downloads. The overall efficiency should not be judged by a single encode energy.

At present, Optimal is smaller than BVX3 / Other3 products; in large-scale distribution, each client can reduce the download of bytes, thus reducing network transmission time and radio/Wi-Fi activity time. After accumulating a large number of iPhones or other clients, the transmission-end savings may be more important than the increased one-time compression cost of the server, but it still needs to be confirmed by the actual network and device energy consumption measurement.

The client only runs decode. Optimal, Lazy2 and general BVX3 use the same format and decoder; when the memory capacity allows and high concurrency is adopted, the estimated memory cost of about 300–350 MB decode RSS may be less than the CPU/transmission saving, so the overall direction is favorable to client-side energy. This is a working hypothesis, not a common conclusion for all iPhone models or memory-pressure situations.

System layer evaluation should use: `one encode energy + all client's transmission energy + all client's decode energy`. The more downloads and the greater the compression size gap, the easier it is to equalize the server-side high encode cost of Optimal; if it is only a single local compression, it may not be cost-effective.

App Store is only an analogy of application scenarios: at present, `bvx3` is a private format, and the actual deployment requires the client to integrate the corresponding decoder, and conform to the platform update, signature and encapsulation process; this document does not claim that the existing format can directly replace the official update format of App Store.

### Test results

`lzfse-test.txt` shows the round-trip and compatibility tests of various data types:
- **Highly duplicate data**: compressed to ~1–2% (from 19.2 KB to 222–235 bytes)
- **Low entropy data**: compressed to 0.3–0.4%
- **Random (uncompressible)**: ~100% size (slightly expanded)
- **Structured data**: 8.5–16.5% compression ratio (Lazy2 is better)
- **Staggered distance mode**: 0.7–0.8% compression ratio
- **Large text sample**: 25.9–26.7% compression ratio (Lazy2 improvement)

All formats are compatible: the output of `other3` and `bvx3` can be decoded by this tool, and Apple Compression framework can decode the `other3` stream.

These figures are just examples. Before formally comparing the performance, please retest with representative data and hardware.
