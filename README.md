#Lzfse2

English | [繁體中文](README.zh-TW.md)

`lzfse2` is an LZFSE command line compression/decompression tool based on Swift. It contains bit-compatible, multi-core encoders and decoders, and also provides an optional private `bvx3` format in exchange for higher compression rates.

## Function

- `other3` is the default engine, which outputs the standard LZFSE stream, which can be decoded by Apple Compression and this tool.
- `apple` is used to use Apple `COMPRESSION_LZFSE` when available.
- `bvx3` uses private expansion blocks with large windows and alphabets. The compression rate may be better, but only this tool can decode.
- The decoder accepts all supported block types, including LZFSE streams generated by Apple.
- Support file, stdin/stdout streaming, and built-in round-trip and compatibility tests.

## Usage

```sh
./lzfse -h
```

```text
Usage: lzfse -encode|-decode [-algo apple|other3|bvx3] [-lazy2|-optimal] [-si|-i input] [-so|-o output] [-test] [-h]
```

Use the default `other3` engine to compress files:

```sh
./lzfse -encode -i input_file -o output_file.lzfse
```

Specify engine compression:

```sh
./lzfse -encode -algo apple -i input_file -o output_file.lzfse.apple
./lzfse -encode -algo bvx3 -i input_file -o output_file.lzfse.bvx3
```

Use `bvx3` high compression rate parser mode to compress tar stream:

```sh
tar -cf - input_dir | ./lzfse -encode -si -o input_dir.lazy2.lzfse -algo bvx3 -lazy2
tar -cf - input_dir | ./lzfse -encode -si -o input_dir.optimal.lzfse -algo bvx3 -optimal
```

Unzip the file:

```sh
./lzfse -decode -i input_file.lzfse -o output_file
```

Decompression `bvx3` Product:

```sh
./lzfse -decode -i file.lzfse -o out.tar -algo bvx3
```

The built-in decoding path of the same tool can also decode the standard LZFSE stream generated by `-algo apple` or Apple Compression:

```sh
./lzfse -decode -i file.lzfse.apple -o out.tar -algo bvx3
```

Through stdin/stdout stream processing:

```sh
cat input_file | ./lzfse -encode -si -so > output_file.lzfse
./lzfse -decode -i input_file.lzfse -so > output_file
```

`-lazy2` and `-optimal` are just the parser / match selection mode of **bvx3 encoder**, and the `bvx3` bitstream format is not changed. The pressed file is still in `bvx3` private format, so you only need to specify `-algo bvx3` when decompressing:

```bash
./lzfse -decode -i file.lzfse -o out.tar -algo bvx3
```

That is:

```bash
./lzfse -encode -si -o a.lazy2.lzfse -algo bvx3 -lazy2
./lzfse -decode -i a.lazy2.lzfse -so -algo bvx3
```

```bash
./lzfse -encode -si -o a.optimal.lzfse -algo bvx3 -optimal
./lzfse -decode -i a.optimal.lzfse -so -algo bvx3
```

The decompression terminal does not need and should not add `-lazy2` or `-optimal`. These two flags have no formatting significance for decode.

### Notes on Unpacking Windows PowerShell tar

Do not use `.\lzfse.exe -decode -so | tar ...` directly in Windows PowerShell. PowerShell may use binary stdout as text pipeline processing and destroy tar stream. Please use `cmd /d /c` instead to let the binary pipe be processed by `cmd.exe`:

```powershell
cmd /d /c ".\lzfse.exe -decode -i ""C:/path/input.lzfse"" -n 8 -so | tar -xf - -C ""C:/path/output-folder"""
```

If the seal is created with the parent relative path, the content path may be `../name/...`; Windows bsdtar will return `Path contains '..'` due to security check. In this case, please remove the frontmost `..` path component when unpacking:

```powershell
cmd /d /c ".\lzfse.exe -decode -i ""C:/path/input.lzfse"" -n 8 -so | tar -xf - --strip-components 1 -C ""C:/path/output-folder"""
```

## Engine

| Engine | Output Compatibility | Description |
| --- | --- | --- |
| `other3` | Standard LZFSE | Default. Multi-core, lazy matching, the output can be decoded by Apple. |
| `apple` | Standard LZFSE | Use Apple Compression framework. |
| `bvx3` | Private format of this tool | Larger windows and alphabets can improve the compression rate; Apple cannot decode. |

When encoding `bvx3`, `-lazy2` and `-optimal` will choose the parser mode that is slower but may improve the compression rate. They will not create different decoding formats; generally, `bvx3`, `bvx3 -lazy2` and `bvx3 -optimal` products all use `-algo bvx3` decoding.

When decoding, `-algo other3` and `-algo bvx3` use the same built-in block decoder. This decoder accepts all supported LZFSE block types, including the standard stream generated by `-algo apple` or Apple Compression. `-algo apple` will use Apple framework decoder instead.


## zsh auxiliary function

This repository contains a `zshrc` example, which can first package the directory into `tar` streaming, and then submit it to this tool for compression.

```zsh
# 解壓常見封存格式。
extract () {
    if [ -f "$1" ] ; then
        case "$1" in
            *.lzfse.bvx3)      echo "lzfse -decode -i $1 -so -algo bvx3   | tar -xf - " ; lzfse -decode -i $1 -so -algo bvx3   | tar -xf -  ;;
            *.lzfse.other3)    echo "lzfse -decode -i $1 -so -algo other3 | tar -xf - " ; lzfse -decode -i $1 -so -algo other3 | tar -xf -  ;;
            *.lzfse.apple)     echo "lzfse -decode -i $1 -so -algo apple  | tar -xf - " ; lzfse -decode -i $1 -so -algo apple  | tar -xf -  ;;
            *.tar.lz4)         lz4 -T0 -d -q -c "$1" | tar -xf - ;;
            *.zst)             zstd -d -c "$1" | tar -xf - ;;
            *.tar.xz)          tar xf "$1" ;;
            *.tar.bz2)         tar xjf "$1" ;;
            *.tar.gz|*.tgz)    tar xzf "$1" ;;
            *.bz2)             bunzip2 "$1" ;;
            *.rar)             unrar e "$1" ;;
            *.gz)              gunzip "$1" ;;
            *.tar)             tar xf "$1" ;;
            *.tbz2)            tar xjf "$1" ;;
            *.zip)             unzip "$1" ;;
            *.Z)               uncompress "$1" ;;
            *.xz)              xz -d "$1" ;;
            *.7z)              7z x "$1" ;;
            *.lz4)             unlz4 "$1" ;;
            *.lzma)            tar --lzma -xvf "$1" ;;
            *.lz4a)            unlz4a "$1" ;;
            *)                 echo "'$1' cannot be extracted via extract()" ;;
        esac
    else
        echo "'$1' is not a valid file"
    fi
}

# 將檔案或目錄打成 tar 串流後，以 LZFSE 壓縮。
lzfseX() {
    if [[ -z "$1" ]]; then
        echo "Usage: lzfseX <file-or-directory> [apple|other3|bvx3]"
        return 1
    fi

    local algo="${2:-other3}"
    local extension="lzfse.other3"
    [[ "$algo" == "apple" ]] && extension="lzfse.apple"
    [[ "$algo" == "bvx3" ]] && extension="lzfse.bvx3"
    [[ "$algo" == "other3" ]] && extension="lzfse.other3"

    echo tar -cf - "$1" "|" lzfse -encode -si -o "$1.$extension" -algo "$algo"
    tar -cf - "$1" | lzfse -encode -si -o "$1.$extension" -algo "$algo"

    echo "--- 壓縮資訊 ---"
    du -sh "$1"
    du -sh "$1.$extension"
}
```

```sh
source ~/.zshrc
```

### RSS and CPU energy consumption trade-off

According to the continuous access estimate of [ `LPDDR_power_estimation/LPDDR_power_info.md`] (LPDDR_power_estimation/LPDDR_power_info.md), LPDDR4X / LPDDR5 is about `150 / 120 mW/GB`. RSS increased from about 60 MB to 300 MB, with an increase of about 240 MB (0.234 GB), corresponding to the additional power of DRAM about `35 / 28 mW`.

If the additional cost of about 20-40% of memory controller / PHY is included, the memory subsystem increment is about `34–49 mW`. EVEN IF THIS IS REGARDED AS THE CONSERVATIVE UPPER LIMIT OF THE WHOLE CONTINUOUS ACTIVITY, RUNNING FOR 40 SECONDS WILL INCREASE ABOUT `1.4–2.0 J`; IF ONLY ABOUT 4 SECONDS, IT WILL INCREASE ABOUT `0.14–0.20 J`.

In the previous controlled round, when the Optimal decode was upgraded from n4 to n40, the RSS increased from `68.5 / 71.1 MB` to `308.9 / 348.9 MB`, and the CPU energy was reduced from `17.13 / 11.33 J` to `8.39 / 5.86 J` (about `-51% / -48%`). CPU savings are much higher than the estimated memory increment of about a few hundredths of a joule in less than a second. Therefore, in the current desktop test and about 300 MB RSS range, it is a better overall choice to prioritize reducing CPU running time/total energy consumption, and about 300 MB RSS can be regarded as conditionally acceptable.

This is a model estimate based on the power consumption of active-memory units, not the actual measurement of this round of DRAM; RSS does not mean that all pages are continuously read and written. The conclusion is only used for energy trade-off, which does not mean that memory capacity, system memory pressure or multi-workload parallel problems can be ignored. The Optimal encode n40 RSS of the latest best-points is about `561.2 / 597.2 MB`, which still obviously exceeds the 300 MB benchmark. We should continue to investigate the life cycle of DP buffer, chunk in-flight and temporary arrays.

### Applicable scenario: server-side update package compression

Optimal compression is suitable for the distribution model of "server-side compression once, client-side download and decompression multiple times", such as large-scale server-side code update, App or game update package, CDN static assets. High-cost encode can be completed offline at the release end and shared by a large number of downloads. The overall efficiency should not be judged only by a single encode energy.

At present, Optimal is smaller than BVX3 / Other3 products; during large-scale distribution, each client can reduce download bytes, thus reducing network transmission time and radio / Wi-Fi activity time. After accumulating a large number of iPhones or other clients, transmission-end savings may be more important than the one-time compression cost of the server, but it still needs to be confirmed by measuring the actual network and device energy consumption.

The client only performs decode. Optimal, Lazy2 and general BVX3 use the same format as decoder; when memory capacity is allowed and high concurrency is adopted, the estimated memory cost of about 300–350 MB decode RSS may be less than CPU/transmission savings, so the overall direction is conducive to client-side energy. This is a working assumption, not a general conclusion for all iPhone models or memory-pressure situations.

System layer evaluation should use: `one-time encode energy + transmission energy of all clients + decode energy of all clients`. The more downloads and the larger the compression size gap, the easier it is to equalize the high encoding cost of Optimal's server-side; if it is only a single local compression, it may not be cost-effective.

App Store is only an analogy of application scenarios: At present, `bvx3` is a private format. The actual deployment requires the client to integrate the corresponding decoder and conform to the platform update, signing and encapsulation processes. This document does not claim that the existing format can directly replace the official update format of the App Store.

### Test results

`lzfse-test.txt` shows the round-trip and compatibility tests of various data types:
- **Highly duplicate data**: compressed to ~1–2% (from 19.2 KB to 222–235 bytes)
- **Low entropy data**: compressed to 0.3–0.4%
- **Random (unpressible)**: ~100% size (slightly expanded)
- **Structured data**: 8.5–16.5% compression ratio (Lazy2 is better)
- **Staggered distance mode**: 0.7–0.8% compression ratio
- **Large text sample**: 25.9–26.7% compression ratio (Lazy2 improvement)

All formats are compatible: the output of `other3` and `bvx3` can be decoded by this tool, and Apple Compression framework can decode the `other3` stream.

These numbers are just examples. Before formally comparing the performance, please retest with representative data and hardware.
