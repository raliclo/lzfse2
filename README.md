# lzfse2

English | [繁體中文](README.zh-TW.md)

`lzfse2` is a LZFSE command-line compression/decompression tool implemented in Swift. It includes bit-compatible, multi-core encoders and decoders, and also provides an optional proprietary `bvx3` format to achieve higher compression rates.

## Functions

- `other3` is the default engine, outputting the standard LZFSE stream, which can be decoded by Apple Compression and this tool.
- `other3 -optimal3` is the standard DP optimal parsing mode in LZFSE format; the compression ratio is better than the usual `other3`, and the output still maintains Apple compatibility.
- When `apple` is available, use Apple `COMPRESSION_LZFSE` to implement it.
- `bvx3` uses a private expansion block, featuring a larger window and alphabet. The compression rate may be better, but only this tool can decode it.
- `bvx3 -lazy2` and `bvx3 -optimal` are private format high-compression parser modes, suitable for offline compression with priority for compression rate.
- Decoders accept all block types supported, including LZFSE streams generated by Apple.
- Supports file streaming, stdin/stdout streaming, and built-in bidirectional and compatibility tests.

## Construction

Compile directly using Swift:

```sh
swiftc -O lzfse-cli.swift -o lzfse
```

`-O` flag enables optimization, including the `@inline(__always)` instruction, to improve hotspot path performance (FSE encoding, bit serialization, decoding). See [OPTIMIZATION.md](OPTIMIZATION.md) for details.

Or execute the auxiliary script:

```sh
./compile.zsh
```

`compile.zsh` will also copy the binary file to `/opt/homebrew/bin`, so this step may require write permissions on the local machine.

## Usage

```sh
./lzfse -h
```

```text
Usage: lzfse -encode|-decode [-algo apple|other3|bvx3] [-lazy2|-optimal|-optimal3] [-si|-i input] [-so|-o output] [-test] [-h]
```

Use the default `other3` engine to compress the file:

```sh
./lzfse -encode -i input_file -o output_file.lzfse
```

Specify engine compression:

```sh
./lzfse -encode -algo apple -i input_file -o output_file.lzfse.apple
./lzfse -encode -algo bvx3 -i input_file -o output_file.lzfse.bvx3
```

Using the Optimal3 parser in the standard LZFSE format (compatible with Apple, but compression is slower):

```sh
./lzfse -encode -algo other3 -optimal3 -i input_file -o output_file.lzfse.other3.optimal3
```

Use the `bvx3` higher compression rate parser mode compression tar stream:

```sh
tar -cf - input_dir | ./lzfse -encode -si -o input_dir.lazy2.lzfse -algo bvx3 -lazy2
tar -cf - input_dir | ./lzfse -encode -si -o input_dir.optimal.lzfse -algo bvx3 -optimal
```

Unzip the file:

```sh
./lzfse -decode -i input_file.lzfse -o output_file
```

Uncompress `bvx3` product:

```sh
./lzfse -decode -i file.lzfse -o out.tar -algo bvx3
```

The built-in decoding path within the same tool can also decode the standard LZFSE streams generated by `-algo apple` or Apple Compression:

```sh
./lzfse -decode -i file.lzfse.apple -o out.tar -algo bvx3
```

Process in a stream through stdin/stdout:

```sh
cat input_file | ./lzfse -encode -si -so > output_file.lzfse
./lzfse -decode -i input_file.lzfse -so > output_file
```

`-optimal3` is just the **parser/match selection mode for other3 encoder**. It uses DP's optimal parsing to improve compression efficiency, but the output remains standard LZFSE/bvx2 bitstream, so the decompression side is identical to the general `other3`, no `-optimal3` is needed:

```bash
./lzfse -encode -i a.tar -o a.lzfse.other3.optimal3 -algo other3 -optimal3
./lzfse -decode -i a.lzfse.other3.optimal3 -so
```

`-lazy2` and `-optimal` are just **bvx3 encoder parser / match selection mode**, and do not change the `bvx3` bitstream format. The output file remains in the private format of `bvx3`, so when decompressing, you only need to specify `-algo bvx3`:

```bash
./lzfse -decode -i file.lzfse -o out.tar -algo bvx3
```

That is:

```bash
./lzfse -encode -si -o a.lazy2.lzfse -algo bvx3 -lazy2
./lzfse -decode -i a.lazy2.lzfse -so -algo bvx3
```

```bash
./lzfse -encode -si -o a.optimal.lzfse -algo bvx3 -optimal
./lzfse -decode -i a.optimal.lzfse -so -algo bvx3
```

The decompression end does not need it, and you should not add `-lazy2` or `-optimal`. These two flags have no format meaning for decoding.

### Windows PowerShell tar unpacking precautions

Do not directly use `.\lzfse.exe -decode -so | tar ...` in Windows PowerShell; PowerShell may treat the binary stdout as a text stream and corrupt the tar stream. Instead, use `cmd /d /c` so that the binary pipe is handled by `cmd.exe`:

```powershell
cmd /d /c ".\lzfse.exe -decode -i ""C:/path/input.lzfse"" -n 8 -so | tar -xf - -C ""C:/path/output-folder"""
```

If the archive is created using a relative path from the parent directory, the content path may be `../name/...`; Windows bsdtar will report `Path contains '..'` due to security checks. In this case, please remove the `..` path component from the beginning when unpacking:

```powershell
cmd /d /c ".\lzfse.exe -decode -i ""C:/path/input.lzfse"" -n 8 -so | tar -xf - --strip-components 1 -C ""C:/path/output-folder"""
```

### Extract tar archive to directory / Decode tar archive to directory

```sh
# 正常解壓 / Normal decode

lzfse -decode -i file.lzfse -debug -so 2>debug/decode_debug.txt | tar -xf - -C /dest
```

## Engine

| Engine | Output Compatibility | Description |
| --- | --- | --- |
| `other3` | Standard LZFSE | Default. Multi-core, lazy matching, output can be decoded by Apple. |
| `other3 -optimal3` | Standard LZFSE | Best DP parsing within the standard format; compression ratio is better than Other3, but encoding is slower and RSS is higher. |
| `apple` | Standard LZFSE | Uses Apple Compression framework. |
| `bvx3` | This tool is in a proprietary format | Larger windows and a larger character set can improve compression rate; Apple cannot decode it. |

The positioning of `other3 -optimal3` is "the optimal parse that can be achieved within standard compatible formats." It is not the same as `bvx3 -optimal`: the latter uses proprietary bvx3 `encodeBlockV3`, has a larger match length and distance expression capability, so the compression ratio is still significantly better than Optimal3, but it lacks Apple compatibility.

When coding `bvx3`, `-lazy2` and `-optimal` will select a slower but potentially higher compression rate parser mode. They will not create different decoding formats; generally, the output of `bvx3`, `bvx3 -lazy2`, and `bvx3 -optimal` all use `-algo bvx3` for decoding.

During decoding, `-algo other3` and `-algo bvx3` use the same built-in block decoder. This decoder accepts all supported LZFSE block types, including standard streams generated by `-algo apple` or Apple Compression. `-algo apple` will then use the Apple framework decoder.


## zsh auxiliary functions

This repository contains a `zshrc` example, which can first package the directory into a `tar` stream and then submit it to this tool for compression.

```zsh
# 解壓常見封存格式。
extract () {
    if [ -f "$1" ] ; then
        case "$1" in
            *.lzfse.other3.optimal3) echo "lzfse -decode -i $1 -so -algo other3 | tar -xf - " ; lzfse -decode -i "$1" -so -algo other3 | tar -xf - ;;
            *.lzfse.bvx3.optimal)   echo "lzfse -decode -i $1 -so -algo bvx3   | tar -xf - " ; lzfse -decode -i "$1" -so -algo bvx3   | tar -xf - ;;
            *.lzfse.bvx3.lazy2)     echo "lzfse -decode -i $1 -so -algo bvx3   | tar -xf - " ; lzfse -decode -i "$1" -so -algo bvx3   | tar -xf - ;;
            *.lzfse.bvx3)      echo "lzfse -decode -i $1 -so -algo bvx3   | tar -xf - " ; lzfse -decode -i $1 -so -algo bvx3   | tar -xf -  ;;
            *.lzfse.other3)    echo "lzfse -decode -i $1 -so -algo other3 | tar -xf - " ; lzfse -decode -i $1 -so -algo other3 | tar -xf -  ;;
            *.lzfse.apple)     echo "lzfse -decode -i $1 -so -algo apple  | tar -xf - " ; lzfse -decode -i $1 -so -algo apple  | tar -xf -  ;;
            *.tar.lz4)         lz4 -T0 -d -q -c "$1" | tar -xf - ;;
            *.zst)             zstd -d -c "$1" | tar -xf - ;;
            *.tar.xz)          tar xf "$1" ;;
            *.tar.bz2)         tar xjf "$1" ;;
            *.tar.gz|*.tgz)    tar xzf "$1" ;;
            *.bz2)             bunzip2 "$1" ;;
            *.rar)             unrar e "$1" ;;
            *.gz)              gunzip "$1" ;;
            *.tar)             tar xf "$1" ;;
            *.tbz2)            tar xjf "$1" ;;
            *.zip)             unzip "$1" ;;
            *.Z)               uncompress "$1" ;;
            *.xz)              xz -d "$1" ;;
            *.7z)              7z x "$1" ;;
            *.lz4)             unlz4 "$1" ;;
            *.lzma)            tar --lzma -xvf "$1" ;;
            *.lz4a)            unlz4a "$1" ;;
            *)                 echo "'$1' cannot be extracted via extract()" ;;
        esac
    else
        echo "'$1' is not a valid file"
    fi
}

# 將檔案或目錄打成 tar 串流後，以 LZFSE 壓縮。
lzfseX() {
    if [[ -z "$1" ]]; then
        echo "Usage: lzfseX <file-or-directory> [apple|other3|optimal3|bvx3|lazy2|optimal]"
        return 1
    fi

    local algo="${2:-other3}"
    local extension="lzfse.other3"
    local flags=("-algo" "$algo")
    [[ "$algo" == "apple" ]] && extension="lzfse.apple"
    [[ "$algo" == "bvx3" ]] && extension="lzfse.bvx3"
    [[ "$algo" == "other3" ]] && extension="lzfse.other3"
    [[ "$algo" == "optimal3" ]] && extension="lzfse.other3.optimal3" && flags=("-algo" "other3" "-optimal3")
    [[ "$algo" == "lazy2" ]] && extension="lzfse.bvx3.lazy2" && flags=("-algo" "bvx3" "-lazy2")
    [[ "$algo" == "optimal" ]] && extension="lzfse.bvx3.optimal" && flags=("-algo" "bvx3" "-optimal")

    echo tar -cf - -C "$(dirname "$1")" "$(basename "$1")" "|" lzfse -encode -si -o "$1.$extension" "${flags[@]}"
    tar -cf - -C "$(dirname "$1")" "$(basename "$1")" | lzfse -encode -si -o "$1.$extension" "${flags[@]}"

    echo "--- 壓縮資訊 ---"
    du -sh "$1"
    du -sh "$1.$extension"
}
```

### RSS and CPU power consumption selection

Based on the continuous access estimation from [ `LPDDR_power_estimation/LPDDR_power_info.md`](LPDDR_power_estimation/LPDDR_power_info.md), LPDDR4X / LPDDR5 is approximately `150 / 120 mW/GB`. RSS increased from about 60 MB to 300 MB, an increase of approximately 240 MB (0.234 GB), corresponding to an additional power consumption for DRAM of about `35 / 28 mW`.

If memory controller / PHY is included again, an additional cost of about 20–40% is added, resulting in an increase in the memory subsystem by approximately `34–49 mW`. Even if this is considered a conservative upper limit for continuous activity, executing for 40 seconds would increase it by approximately `1.4–2.0 J`; if it is only about 4 seconds, it would increase by approximately `0.14–0.20 J`.

During the previous controlled phase, when Optimal decode was upgraded from n4 to n40, RSS increased from `68.5 / 71.1 MB` to `308.9 / 348.9 MB`, and CPU energy decreased from `17.13 / 11.33 J` to `8.39 / 5.86 J` (approximately `-51% / -48%`). The CPU energy savings level is far higher than the estimated memory increase of less than one percent of a joule over a period of less than 1 second. Therefore, in current desktop tests and within a range of approximately 300 MB RSS, prioritizing reducing CPU execution time/total energy consumption is the better overall compromise; approximately 300 MB RSS can be considered a conditional acceptance.

This is a model estimate based on active-memory unit power consumption, not a real-world DRAM measurement for this iteration; RSS does not mean that all pages are continuously read and written. The conclusion is only for energy trade-offs and does not imply that memory capacity, system memory pressure, or concurrent workload issues can be ignored. The latest best-points Optimal encode n40 RSS values are `573.2 MB` (claw-code) and `599.2 MB` (llama.cpp)—taken from the "highest Encode RSS" column for `best_points/best_points.md` —still clearly exceed the 300 MB benchmark. Further investigation into DP buffer, chunk in-flight, and temporary array lifecycle is recommended.

### Applicable scenarios: Server-side update package compression

Optimal compression is suitable for distribution models that involve "one-time compression on the server side and multiple downloads and decompression on the client side," such as large server-side code updates, App or game update packages, and static assets from CDN. High-cost encoding can be completed offline on the distribution server and distributed across a large number of download sessions, so the overall efficiency should not be solely determined by the single-time encoding energy.

Currently, Optimal produces smaller results than BVX3 / Other3; when distributed at scale, each client can reduce the amount of downloaded bytes, thereby lowering network transmission time and radio/Wi-Fi activity time. When a large number of iPhones or other clients are accumulated, the savings on the transmission side may be more important than the one-time compression cost of the server, but it still needs to be measured and confirmed by actual network and device energy consumption.

The client side only executes decode. Optimal, Lazy2, and general BVX3 use the same format and decoder; when memory capacity allows and concurrency is high, the estimated memory cost of about 300–350 MB of decode RSS may be less than CPU/bandwidth savings, so overall the direction is favorable for client-side energy. This is a working assumption and not a universal conclusion for all iPhone models or memory-pressure scenarios.

The system-level evaluation should use: `one encode energy + the transmission energy of all clients + the decode energy of all clients`. The more times you download, the greater the difference in compression size, and the more easily the optimal server-side high encode cost can be spread out; if it is only local compression on a single occasion, it may not be cost-effective.

The App Store is only for illustrative purposes: Currently, `bvx3` is in a private format, and actual deployment requires integrating the corresponding decoder on the client side and complying with platform update, signing, and packaging processes; this document does not claim that the current format can directly replace the official update format of the App Store.

### Test results

`lzfse-test.txt` demonstrates tests of bidirectional and compatibility for various data types:
- **Highly repetitive data**: Compressed to ~1–2% (from 19.2 KB to 222–235 bytes)
- **Low entropy data**: Compressed to 0.3–0.4%
- **Random (unpressable)**: ~100% size (slightly inflated)
- **Structured data**: 8.5–16.5% compression ratio (Lazy2 is better)
- **Interlace distance mode**: 0.7–0.8% compression ratio.
- **Large text sample**: 25.9–26.7% compression ratio (Lazy2 improvement)

All formats are compatible: the output of `other3` and `bvx3` can be decoded by this tool, and the Apple Compression framework can decode the `other3` stream.

These numbers are only for example. Please retest with representative data and hardware before making a formal comparison of performance.
